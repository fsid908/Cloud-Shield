# Cloud-Shield API Design

## 1. Overview

Cloud-Shield exposes HTTP API endpoints through a Node.js and Express.js backend.

The API supports:

- User registration and authentication.
- Access-token refresh and logout.
- File upload and metadata retrieval.
- File integrity verification.
- Backup-based file recovery.
- Recent file activity retrieval.
- Suspicious activity analysis.
- Security event history retrieval.
- Health status checks.

The API uses a consistent JSON response format through the application's response utility.

## 2. Base URL

For local development, the API base URL depends on the server configuration.

Example:

`http://localhost:<PORT>`

Replace `<PORT>` with the port configured for the backend.

The application's route index mounts API route groups. The final endpoint paths documented below are derived from those mount paths and the individual route definitions.

Production deployments should use HTTPS.

## 3. Response Format

Successful responses use the application's success response utility.

Example:

```json
{
  "success": true,
  "message": "Operation completed successfully.",
  "data": {}
}
```

Error responses are handled by the application's centralized error-handling middleware.

Example:

```json
{
  "success": false,
  "message": "An appropriate error message."
}
```

The exact error status and message depend on the error-handling implementation and the specific failure.

## 4. Authentication

### Authentication Mechanism

The login controller sets two cookies:

- `accessToken`
- `refreshToken`

Both cookies are configured with `HttpOnly` and `SameSite=Strict`.

The `Secure` flag is enabled when `NODE_ENV` is set to `production`.

The access-token cookie has a configured lifetime of 15 minutes.

The refresh-token cookie has a configured lifetime of 4 hours.

The refresh endpoint rotates tokens through the refresh service and returns replacement cookies.

Authentication and refresh behavior should be tested against the current middleware and service implementations.

### Protected Endpoints

The following endpoints explicitly use the authentication middleware:

- `GET /auth/me`
- `POST /files`
- `GET /files/:fileId`
- `GET /files/:fileId/integrity`
- `POST /files/:fileId/recover`
- `GET /security/activity`
- `GET /security/detection`
- `GET /security/events`
- `GET /security/activity-analysis`

The registration, login, logout, refresh, and health routes do not attach the authentication middleware directly in their route definitions.

This does not mean those endpoints have no security requirements. Their controller and service behavior must be considered separately.

## 5. Health Check

### `GET /health`

Checks whether the API can return its health status.

Authentication: Not required by the route definition.

Success status: `200 OK`.

The response data is generated by the health service.

Example request:

`GET /health`

## 6. Authentication Endpoints

### `POST /auth/register`

Registers a user.

Authentication: Not required by the route definition.

Request validation: Registration schema validation middleware.

The controller passes the request body to the authentication service.

Success status: `201 Created`.

Example request body:

```json
{
  "fullName": "Example User",
  "email": "user@example.com",
  "password": "replace-with-a-valid-password"
}
```

The exact required fields and password constraints are defined by the registration validator and authentication service.

### `POST /auth/login`

Authenticates a user and establishes the token cookies.

Authentication: Not required by the route definition.

Request validation: Login schema validation middleware.

Request body:

```json
{
  "email": "user@example.com",
  "password": "replace-with-the-account-password"
}
```

On successful authentication, the controller sets the `accessToken` and `refreshToken` cookies.

The response returns user information without including the tokens in the response data.

Success status: `200 OK`.

### `GET /auth/me`

Returns information about the authenticated user.

Authentication: Required.

Success status: `200 OK`.

The response data comes from the authenticated user object populated by the authentication middleware.

### `POST /auth/logout`

Attempts to revoke the refresh session and clears the access-token and refresh-token cookies.

Authentication: No authentication middleware is attached directly to this route.

The controller reads the refresh token from the cookie and passes it to the refresh service for revocation.

Success status: `200 OK` when the operation completes successfully.

### `POST /auth/refresh`

Refreshes the access token using the refresh token cookie.

Authentication: No authentication middleware is attached directly to this route.

The refresh service validates and rotates the refresh session.

On success, the controller sets replacement access-token and refresh-token cookies.

Success status: `200 OK`.

The response does not expose the new tokens in its JSON data.

## 7. File Endpoints

### `POST /files`

Uploads a file for the authenticated user.

Authentication: Required.

Content type: Multipart form data.

Form field:

- `file`: The file to upload.

The upload middleware processes the file and makes it available to the controller.

The controller passes the authenticated user's identifier and uploaded file to the file service.

Success status: `201 Created`.

A request without an uploaded file is rejected with `400 Bad Request`.

Example:

```bash
curl -X POST "http://localhost:<PORT>/files" \
  -F "file=@example.pdf" \
  --cookie "accessToken=<ACCESS_TOKEN>"
```

This example illustrates the multipart request shape. Authentication cookies should be managed securely, and real tokens must never be committed to source control.

### `GET /files/:fileId`

Retrieves file information for a specific file.

Authentication: Required.

Path parameter:

- `fileId`: Identifier of the requested file.

The controller passes the file identifier and authenticated user's identifier to the file service.

The service is responsible for enforcing file ownership.

Success status: `200 OK`.

### `GET /files/:fileId/integrity`

Checks the integrity of a file.

Authentication: Required.

Path parameter:

- `fileId`: Identifier of the file to check.

The controller calls the integrity service with the file identifier and authenticated user's identifier.

Success status: `200 OK`.

The exact integrity result structure is defined by the integrity service.

### `POST /files/:fileId/recover`

Attempts to recover a file from its trusted backup.

Authentication: Required.

Path parameter:

- `fileId`: Identifier of the file to recover.

The controller calls the recovery service with the file identifier and authenticated user's identifier.

Success status: `200 OK` when recovery completes successfully.

The recovery service is responsible for implementing the recovery workflow and its associated checks.

## 8. Security Activity Endpoints

### `GET /security/activity`

Retrieves recent file integrity activity.

Authentication: Required.

Query parameters:

| Parameter | Default | Description |
|---|---|---|
| `window` | `30` | Time window in seconds passed to the activity service |

Example:

`GET /security/activity?window=60`

The controller converts the query parameter to a number before calling the detection service.

The exact accepted range and validation behavior must be verified in the service implementation.

Success status: `200 OK`.

### `GET /security/detection`

Analyzes recent activity for suspicious signals.

Authentication: Required.

Query parameters:

| Parameter | Default | Description |
|---|---|---|
| `window` | `30` | Time window in seconds passed to the detection engine |

Example:

`GET /security/detection?window=60`

The controller calls the detection engine service to analyze suspicious activity.

Success status: `200 OK`.

This endpoint performs analysis. Its existence alone does not establish that malicious processes are automatically blocked.

### `GET /security/events`

Retrieves security events belonging to the authenticated user.

Authentication: Required.

Query parameters:

| Parameter | Default | Constraints |
|---|---|---|
| `page` | `1` | Positive safe integer |
| `limit` | `10` | Integer between 1 and 100 |

Example:

`GET /security/events?page=1&limit=10`

Success status: `200 OK`.

Example response:

```json
{
  "success": true,
  "message": "Security events retrieved successfully.",
  "data": {
    "events": [],
    "pagination": {
      "page": 1,
      "limit": 10,
      "total": 0,
      "totalPages": 0
    }
  }
}
```

The `events` array contains the records returned for the requested page.

The `pagination` object contains:

- `page`: Current page number.
- `limit`: Maximum number of records requested.
- `total`: Total matching records for the authenticated user.
- `totalPages`: Number of pages calculated from the result count and page size.

Events are ordered by descending creation time, followed by descending document identifier.

The service scopes the query to the authenticated user's identifier.

Invalid pagination values are rejected by the service validation.

### `GET /security/activity-analysis`

Analyzes recent file activity for the authenticated user.

Authentication: Required.

Query parameters:

| Parameter | Default | Description |
|---|---|---|
| `window` | `30` | Time window in seconds passed to the analysis service |

Example:

`GET /security/activity-analysis?window=60`

Success status: `200 OK`.

The controller passes the authenticated user's identifier and the selected time window to the activity analysis service.

The exact analysis rules and response structure are defined by that service.

## 9. Error Handling

Controllers forward errors to the centralized error-handling middleware.

Potential error categories include:

- Authentication failures.
- Authorization or ownership failures.
- Invalid request parameters.
- Request validation failures.
- Missing files.
- Integrity verification failures.
- Recovery failures.
- Database errors.
- Unexpected server errors.

The actual HTTP status and response message depend on the error raised and the middleware implementation.

Client responses must not expose stack traces, secrets, token values, or internal filesystem details.

## 10. Security Considerations

- Require authentication for protected endpoints.
- Enforce resource ownership in the backend.
- Validate all untrusted input.
- Keep authentication tokens out of response bodies and application logs.
- Protect refresh-token rotation and revocation.
- Validate uploaded files and enforce file-size restrictions.
- Prevent path traversal and unsafe file path construction.
- Verify backup integrity before recovery.
- Apply appropriate rate limits to sensitive endpoints.
- Use HTTPS in production.
- Review cookie and cross-origin settings before deployment.
- Avoid exposing internal error details to clients.
